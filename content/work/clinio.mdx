<Problem>
Small clinics run on spreadsheets, WhatsApp, and paper appointment books. Commercial practice management software exists but it's priced for hospital systems — monthly SaaS fees that a 3-doctor clinic can't justify for a booking calendar and a patient list. The gap is a system that covers the actual workflow: receptionist books an appointment, doctor sees the patient queue for the day, admin generates an invoice, owner looks at the weekly stats. Nothing more, nothing less.

The design constraint that shaped everything: each of those four jobs is a different person with different permissions looking at the same data. Clinio is one application that shows each role exactly its slice — not four portals, not one God-mode screen.
</Problem>

<Architecture diagram="/diagrams/clinio.svg">
The backend is a single Express + Prisma application with PostgreSQL as the data store. Prisma handles the schema, migrations, and typed queries — the data model covers Users (with roles), Patients, Doctors, Appointments, Invoices, and the relations between them. JWT handles auth, and the middleware chain is deliberately explicit: helmet, CORS, rate limiting, audit capture, then role-guarded routes for receptionist, doctor, and admin.

The frontend is a React + Vite SPA with React Router and Tailwind CSS. Pages map directly to the clinic workflow: patient intake form, appointment calendar against real doctor availability (working hours, available days), invoice generation with PDF export, and an analytics dashboard. An emerald-and-teal identity, brand tokens centralized in a single theme file.
</Architecture>

<Decisions subtitle="Three decisions that kept a four-role system simple.">

<Decision
  number="01"
  title="PostgreSQL over MongoDB"
  chose="PostgreSQL with Prisma ORM and typed schema"
  rejected="MongoDB + Mongoose, SQLite"
  why="Appointments, invoices, and patient records are inherently relational. A patient has many appointments; an appointment references a doctor and a patient; an invoice references an appointment. Document databases flatten these relations into embedded arrays or manual join logic. PostgreSQL handles them natively with foreign keys and joins. Prisma generates TypeScript types from the schema automatically, so the API layer is always type-safe against the database shape."
/>

<Decision
  number="02"
  title="Express over NestJS"
  chose="Express with manual middleware composition"
  rejected="NestJS, Fastify, Hono"
  why="NestJS's decorator-based structure adds significant boilerplate for a project where the route surface is known and bounded. Express lets you see the full middleware chain at a glance — auth, rate limit, audit log, error handler — without IoC container concepts getting in the way. In a system where three roles have different write permissions on the same tables, being able to read the entire authorization path in one file is worth more than framework structure."
/>

<Decision
  number="03"
  title="One SPA with role-scoped views over separate portals"
  chose="A single React app where routes and data are gated by role"
  rejected="Separate receptionist/doctor/admin frontends, server-rendered per-role dashboards"
  why="The three roles differ in what data they may touch, not in what kind of interface they need — everyone gets lists, forms, and a calendar. Splitting by role would triple the surface to build and deploy for zero user benefit. Role scoping lives in two places that must agree: route guards in the SPA decide what renders, and requireRole middleware on the API decides what executes. The API is the source of truth; the UI is just a polite filter."
/>

</Decisions>

<Code title="Role-based route protection">
{`// backend/src/middleware/auth.js
export const requireRole = (...roles) => (req, res, next) => {
  if (!req.user) return res.status(401).json({ error: "Unauthorized" });
  if (!roles.includes(req.user.role)) {
    return res.status(403).json({ error: "Insufficient permissions" });
  }
  next();
};

// backend/src/routes/admin.js
router.get("/users", authenticate, requireRole("admin"), async (req, res) => {
  const users = await prisma.user.findMany({
    select: { id: true, name: true, email: true, role: true },
  });
  res.json(users);
});

// Receptionist books appointments; only admin can see all users.
// Doctor routes are protected separately — doctors only see their own queue.`}
</Code>

<Outcomes>
<Works>
- Patient intake with full medical history, allergies, insurance fields
- Appointment booking with doctor availability grid (working hours, available days)
- Invoice generation linked to appointments, with branded PDF export
- Role-based access: receptionist, doctor, admin each see their workflow
- Analytics dashboard: daily appointment counts, revenue by period, patient stats
- Audit logging on all mutations (who changed what and when)
- Email notifications via Resend (appointment reminders, invoice receipts)
</Works>
<DoesntYet>
- Multi-clinic tenancy — currently single-clinic per deployment
- Calendar sync (Google Calendar, iCal export)
- Insurance claim submission — invoice data is captured but not filed
- Mobile app — the React SPA is responsive but not native
</DoesntYet>
</Outcomes>

<Lessons>
Prisma's migration workflow is the best part of the stack. Schema changes are tracked as versioned migration files, and the generated types update automatically. The discipline of "change the schema first, then the code" produces a cleaner API layer than writing the API and inferring the schema from it.

The audit log should have been designed as a first-class data structure from day one. I added it midway as a middleware side-effect, and a proper `AuditLog` model in Prisma is what makes it queryable — "show me all changes to patient ID X in the last 30 days" — rather than something you grep.

The booking grid earned its iteration time. The first version was a naive day calendar; the version that survived checks the doctor's working hours and available days before offering a slot. That one change moved the product from "digital appointment book" to "thing the receptionist trusts" — most of the perceived quality of Clinio lives in that grid.
</Lessons>
