<Problem>
Picture where a service business actually wins or loses a customer. Someone with a problem they finally want handled — a toothache, a lawsuit, a leaking roof, a stalling company — works up the nerve to fill in a contact form, hits send, and gets "thanks, we'll be in touch." Then nothing. So they open the next two tabs and enquire there too. Whoever replies first, sounding like a real person who actually read the question, gets the call. The firm that gets back to them tomorrow morning gets a "thanks, but we've gone with someone else."

This isn't a hunch. A lead answered within five minutes is ~21× more likely to convert than one answered after thirty, 78% of buyers go with the company that responds first, and most businesses miss that five-minute window entirely. What loses the deal is never the prettiness of the page — it's the dead air after the form. And there's a second person to keep in mind: whoever wants to *sell* a page like this. A clinic, a law firm, a consultancy, and a gym all need the same shape of site in different words and colours, and none of them will pay to have it rebuilt from scratch.

Meridian is built for both heads. For the prospect, it doesn't just promise a fast reply — the hero *shows* one happening, then the real form delivers it: a tailored, on-brand answer in seconds, so they feel heard before a competitor has opened the email. For the business, every enquiry also lands pre-qualified — category, urgency, the right service — so they can reply first and win. And for whoever is reselling it, the entire site (brand, colours, every line of copy) reskins to a new industry by editing one config file.
</Problem>

<Architecture diagram="/diagrams/meridian.svg">
The project is two parts with different natures. The site is hand-coded static files (`index.html`, `contact.html`, `style.css`) painted by a small vanilla-JS render engine (`render.js`) from one config (`config.js`). No framework, no build step — a landing page lives or dies on load speed, and speed is conversion. Every word and colour lives in the config; the theme is three CSS custom properties (`--accent`, `--accent-2`, `--accent-ink`) that every gradient, glow, and chip derives from. Switching industry re-themes and re-renders the page in place, and the chosen skin persists across pages via `localStorage`.

The one piece of backend is a Vercel serverless function (`/api/consult`). The contact form posts to it; the function applies a honeypot and dual-window rate limit, validates the submission, then makes a single structured call to Gemini. The prompt locks the model to one job — acknowledging enquiries and bookings — and the response carries an `onTopic` flag: anything else (code generation, essays, planning, general questions) is refused server-side with a fixed reply, so the AI can't be turned into free general-purpose compute. On a genuine enquiry Gemini returns a warm, on-brand acknowledgement for the visitor plus an internal routing summary (category, urgency, suggested service, notes). The prompt is templated with the visitor-supplied brand and industry, and routing categories are industry-agnostic so the same endpoint serves every skin.
</Architecture>

<Decisions subtitle="Three decisions that made it a product, not a page.">

<Decision
  number="01"
  title="White-label by config, not per-client rebuilds"
  chose="A single config.js (brand, 3 theme colours, all copy per industry) + CSS-variable theming"
  rejected="Duplicating the codebase per client, a CMS, or a drag-and-drop page builder"
  why="The resale unit is a reskin — brand, palette, words — not a rebuild. Pushing every string and colour into one file (and reducing the palette to three CSS variables) is what turns 'a site' into a sellable, reskinnable product. If copy had stayed in the HTML, it could never resell. Five industry skins ship in one codebase: consulting, law, dental, home services, fitness."
/>

<Decision
  number="02"
  title="Hand-coded static over a framework or no-code builder"
  chose="Plain HTML/CSS with a tiny vanilla-JS render engine"
  rejected="Next.js, Astro, or a no-code site builder"
  why="A marketing page should load instantly and have its polish in CSS, not in a runtime. No build step, trivially hostable, and the engineering signal is a clean data-driven render rather than framework boilerplate. The 2026 design language — aurora gradients, glassmorphism, a bento services grid — is all CSS over a tiny render engine."
/>

<Decision
  number="03"
  title="Stateless one-shot intake over a chatbot"
  chose="Validate → call Gemini once → return acknowledgement + routing summary"
  rejected="A stateful, multi-turn chatbot on the contact form"
  why="A visitor submitting a form wants confirmation, not a conversation. A one-shot constraint kept the function small and trivially testable — one input, one deterministic output shape — and resisted the scope creep of session state, history, and moderation that a chatbot drags in."
/>

</Decisions>

<Code title="The white-label core: one config entry, three theme tokens">
{`// config.js — one entry per client; this file IS the product
MERIDIAN_CONFIG.industries.dental = {
  brand: { name: "Brightway", suffix: "Dental Studio", email: "smile@…" },
  theme: { accent: "#38bdf8", accent2: "#5eead4", accentInk: "#03121c" },
  hero: { /* … */ }, services: { /* … */ },
  pricing: { /* … */ }, faq: [ /* … */ ],
};

// render.js — switching skin re-themes + re-renders in place
function switchTo(key) {
  const d = MERIDIAN_CONFIG.industries[key];
  const r = document.documentElement.style;
  r.setProperty("--accent",     d.theme.accent);   // every gradient,
  r.setProperty("--accent-2",   d.theme.accent2);  // glow and chip
  r.setProperty("--accent-ink", d.theme.accentInk);// derives from these
  renderHero(d.hero); renderServices(d.services);
  renderPricing(d.pricing); renderFaq(d.faq); /* … */
  localStorage.setItem("meridian-industry", key);  // persists across pages
}`}
</Code>

<Outcomes>
<Works>
- Hand-coded static site, fully config-driven — five industry skins ship in one codebase (consulting, law, dental, home services, fitness)
- One-file reskin: brand, three theme colours, and all copy per industry; live switcher, `?industry=` override, and `localStorage` persistence
- Conversion-first sections: an animated live AI-intake demo in the hero, count-up stats, bento services, measured results, transparent pricing, a risk-reversal guarantee, and an FAQ accordion
- AI intake: serverless function returns a tailored, on-brand acknowledgement for the visitor plus a structured routing summary for the business
- Scope-locked AI — handles enquiries and bookings only; off-topic or jailbreak attempts get a server-side canned refusal (the model's text is never echoed), with output sanitising and length caps
- Abuse protection: honeypot, dual-window in-memory rate limit, and an optional durable Upstash layer; XML-framed, untrusted-by-default enquiry input
- Mobile-first and reduced-motion aware: stacked CTAs, compact controls, touch feedback, and a sticky mobile CTA bar
</Works>
<DoesntYet>
- Booking is a drop-in slot for Calendly / Cal.com — not a built calendar
- The routing summary isn't persisted in the demo — production needs a CRM/Sheet/Slack webhook destination
- Durable rate limiting is opt-in (Upstash REST) — without those env vars the in-memory limiter resets on cold start
- The scope gate blocks misuse, but there's no dedicated harmful-content classifier — a compliance deployment would add one
</DoesntYet>
</Outcomes>

<Lessons>
The product insight beat the design polish. What sells a service business isn't a nicer hero — it's replying first. Building the hero to *demonstrate* instant intake (an enquiry being answered in seconds, auto-tagged and routed) rather than to describe it is the entire pitch, and it's what reframed a generic consultancy site into something sellable.

White-label is an architecture decision, not a theming afterthought. Reducing the palette to three CSS variables and moving every word into one config is the difference between "a site I built" and "a product I can resell to the next client by editing one file." Had the copy stayed in the markup, none of that would be true.

Replacing the earlier Webflow approach with hand-coded static was the right call for this use case: faster load, no build step, and the engineering signal is a clean, data-driven render. The first version leaned on a no-code framing; the rebuild made that unnecessary — it's genuinely custom now, and honest by construction.

Keeping the AI scope tight paid off. A stateless one-shot intake stayed under ~80 lines and trivially testable. On a build this small, scope discipline is the whole game.
</Lessons>
