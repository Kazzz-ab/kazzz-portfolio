<Problem>
A small law firm has the same operational needs as a small clinic: intake new clients, track active matters, schedule attorney time, generate invoices. The vocabulary is different — clients not patients, cases not appointments, attorneys not doctors — and some business rules differ (a case spans months not minutes; billing is by hours not by visit). But the underlying system is the same.

CounselFlow is the second product on the ClinicFlow platform. It exists to make a specific point: the architecture decision in ClinicFlow to share a pattern rather than share code is what made this possible. Building CounselFlow took roughly 40% of the time ClinicFlow did.
</Problem>

<Architecture diagram="/diagrams/clinicflow-platform.svg">
CounselFlow shares the architectural blueprint of ClinicFlow exactly: Express backend, Prisma ORM, PostgreSQL, React + Vite frontend with Tailwind and React Router. The domain model replaces Patients with Clients, Doctors with Attorneys, and Appointments with Cases. Cases have a status lifecycle (intake → active → closed) that Appointments don't need, and billing is tracked by hourly rate rather than fixed consultation fee.

The backend route structure mirrors ClinicFlow's — auth, clients, attorneys, cases, invoices, stats, notifications, analytics, admin — with domain-appropriate validation rules at each endpoint. The frontend page structure is identical at the router level; the components use legal vocabulary throughout.
</Architecture>

<Decisions subtitle="Two decisions specific to CounselFlow, on top of the ClinicFlow foundations.">

<Decision
  number="01"
  title="Case status lifecycle over appointment state"
  chose="Explicit case status enum: intake → active → pending_close → closed"
  rejected="Re-using the appointment booking model with status flags"
  why="A legal case has a lifecycle measured in months with meaningful state transitions: the firm takes on a client (intake), works the matter (active), prepares to close (pending_close), and archives it (closed). Appointment status (scheduled/completed/cancelled) doesn't map to this. The status enum enforces valid transitions server-side and lets the analytics surface case-level metrics — active caseload, average time-to-close — that appointment counts can't express."
/>

<Decision
  number="02"
  title="Hourly billing model over fixed-fee invoicing"
  chose="Invoice line items with hourly_rate × hours_worked + fixed disbursements"
  rejected="Copying ClinicFlow's fixed consultation-fee invoice model"
  why="Legal billing is time-based. A fixed-fee invoice model from ClinicFlow would require hacking the data model to express hourly work. The invoice schema in CounselFlow has a `billingType` field (hourly or fixed) and line items that capture hours worked when billing is hourly. This is a 20-line schema change that makes the invoicing model honest about the domain it serves."
/>

</Decisions>

<Code title="Case status transitions enforced server-side">
{`// backend/src/routes/cases.js
const VALID_TRANSITIONS = {
  intake:         ["active"],
  active:         ["pending_close", "intake"],
  pending_close:  ["closed", "active"],
  closed:         [], // terminal state
};

router.patch("/:id/status", authenticate, requireRole("admin", "attorney"),
  async (req, res) => {
    const { status: nextStatus } = req.body;
    const caseRecord = await prisma.case.findUniqueOrThrow({ where: { id: req.params.id } });

    const allowed = VALID_TRANSITIONS[caseRecord.status] ?? [];
    if (!allowed.includes(nextStatus)) {
      return res.status(400).json({
        error: \`Cannot transition from \${caseRecord.status} to \${nextStatus}\`,
      });
    }

    const updated = await prisma.case.update({
      where: { id: req.params.id },
      data: { status: nextStatus },
    });
    res.json(updated);
  }
);`}
</Code>

<Outcomes>
<Works>
- Client intake with matter type, conflict-of-interest notes, referral source
- Case tracking with status lifecycle (intake → active → pending_close → closed)
- Attorney scheduling with availability grid (mirrors ClinicFlow doctor availability)
- Hourly + fixed-fee invoicing with line items
- Active caseload and time-to-close analytics dashboard
- Role-based access: paralegal, attorney, admin
- Email notifications via Resend (case status updates, invoice receipts)
</Works>
<DoesntYet>
- Time tracking integration — hours are entered manually on invoice line items
- Document management — matter documents are referenced by name, not stored
- Client portal — clients cannot log in to view their case status
- Court date calendar sync
</DoesntYet>
</Outcomes>

<Lessons>
The 40% build-time figure for CounselFlow vs ClinicFlow is the concrete payoff of the shared-pattern architecture. The decisions that took the most time in ClinicFlow — auth model, role-based middleware, Prisma schema conventions, invoice data model — were already solved. CounselFlow was a domain translation, not a ground-up build.

The case status lifecycle was the right call but I implemented the transition validation server-side only. The frontend still allows selecting any status in the dropdown and shows the error after the API rejects it. A better UX would disable invalid transitions in the UI before the call is made — the valid transitions map should live in a shared types package consumed by both front and back.

If this were a real product, the "doesn't yet" list for both ClinicFlow and CounselFlow converges on the same gap: a client/patient-facing portal. That's the next meaningful feature for both, and it's the case for extracting the shared auth layer into a proper shared package rather than copy-pasting the pattern again.
</Lessons>
